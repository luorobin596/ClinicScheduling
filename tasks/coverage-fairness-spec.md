# 修改規格：最低骨科覆蓋修補與公平性調整

狀態：待審閱提案，尚未實作。2026-10-16。
依賴：[逐人來源規格](staff-assignment-provenance-spec.md)。實作次序與任務以 [plan.md](plan.md)、[todo.md](todo.md) 為準。

## 1. 目標、範圍與事實基準

保留已採用的成對正反序輪轉及原始 C→AC→A→B→週六流程，於儲存前增加覆蓋修補、保持人數的公平性交換及完整驗證。來源修正屬前置能力，不與本規格混為同一項改動。

已重現：新輪轉的同批 100 組排班中，84 組至少一日骨科最低覆蓋失敗，共 101 個失敗日；76 次在 11/30 缺 B，24 個失敗日當日無指定休假。診斷分類為 70 日有可直接補班的人、31 日需重新安排或進一步分析，後者不是無解證明。

基準檔：tests/fairness-paired-rotation-100-2026-11.json。須凍結其 100 組 seed/events/leaveSummary 及版本雜湊；不得重新抽樣、重新篩掉修補不成功者，也不能用另一批意願宣稱改善。

非目標：兼職排班、跨月順位延續、讀取 Sheet REQUIREMENT、全域最優保證、永久調整歷程、Sheet 欄位擴充。

## 2. 輸入、狀態與共享限制

輸入是當月有效 FT、營業日期、固定小兒規則、正規化 requests 及逐人 metadata/constraints。同一次運算從開始至儲存使用同一份意願快照；不得在搜尋中重新讀 Sheet 取得不同意願。

候選同時檢查：原始指定上班必須仍在、指定休假不能排入、固定小兒/代班不變、員工同班不可跨科重複、每天最多兩班、骨科不得超過當日班別設定上限。個人 A/B/C 週目標是軟配額，不能阻止最低覆蓋修補。

平日最低覆蓋：不同 ORTHO 員工 ≥2 且 ORTHO A/B/C 各 ≥1。週六：不同 ORTHO 員工 ≥1，不另新增 AB 各一人的要求。閉診日豁免，小兒永不替代骨科覆蓋。

11 月九天休假含五個週日；其餘八個半天額度。全天休 ABC off 扣二，半天休一班 fixed/另兩班 off 扣一，指定雙班扣零。這是模擬/意願分類，不將實際空班數當作新增指定休假。

## 3. 分階段驗證，避免規格互相矛盾

| 階段 | 必須通過 | 可保留的缺失 |
|---|---|---|
| 僅改來源的回歸 | metadata/constraints 正確；合法基準的人選與班數不變 | 原有最低覆蓋失敗，不得藉此偷偷改班 |
| 初始班表產生 | 原始限制、個人上限、站別及骨科上限 | 最低覆蓋可不足，進修補 |
| 覆蓋修補候選 | 共同限制；覆蓋缺失嚴格減少 | 尚未修完的其他日期可不足 |
| 公平性候選 | 最低覆蓋全部成立；修補後每個 date/shift/station 人數不變 | 不要求每人週週 1 AC/2 BC/2 AB |
| 最終儲存 | 全部共同限制、最低覆蓋、來源完整性及輸出列格式 | 三人需求未滿可保留給兼職 |

原始意願若要求某人三班、同班 fixed/off 衝突或固定班已超額，先報 INPUT_CONFLICT，不讓新搜尋去移動意願「解決」。合法案例來源修改前後等價；不承諾非法舊輸入仍照舊產生班表。

## 4. 覆蓋修補候選與接受規則

每個營業日的缺失集合為 (date, missingShift) 及 (date, staffShortage)，其中 staffShortage=max(0,minStaff-distinctOrthoStaff)。覆蓋損失 L=缺少時段數+所有日人數不足量。排序按可行人選少、日期早；平手按 staff_id、班別穩定決定。

依序搜尋三層候選：

1. 不增總班數的同日改班/轉移/交換。
2. 不增總班數的跨日移動/交換及最多兩個原子操作的組合。
3. 前兩層找不到改善時才新增一班；多個新增候選仍以公平性選擇。

每層須評估其預算內所有合法候選後選最佳，不採第一個可用員工。接受組合後 L 必須嚴格下降；每個日期人數不足量不可增加，已覆蓋的時段不得變無人。組合按最終狀態驗證，中間試算不得提交。先比較 L 改善量，再比較第 5 節公平性向量、修改量及穩定排序。每次接受後重算候選及統計。

修補可以接受公平性代價以達硬條件，必須記錄其前後指標；公平性階段再改善。若最後仍有缺失，禁止儲存/前台匯出；保留診斷與初始/最佳試算快照，不重新抽樣讓失敗消失。

## 5. 一致的公平性統計與明確評分（優先序依使用者修訂）

對每位有效 FT，跨 ORTHO/PEDS 合併每日班別，每班四小時；同班重複是錯誤，不可去重後隱藏。月 AC/BC/AB 含週六，完整週平日另作診斷，不把短週強制套配額。

自願單節只認原始本人意願：實際一班 fixed，其他可營業時段全 off；週六只看 A/B。PEDS 的 FT_FIXED/AUTO_COVER 不表示本人自願；若同時存在本人半天休意願則依本人意願排除。指定雙班照常計班型，並保持兩班鎖定。

對任何員工計數向量 x，R(x)=max(x)-min(x)，Q(x)=N×Σx²-(Σx)²。N 為同批有效 FT 數，這是非負整數離散度；少於一位 FT 的輸入不進公平性搜尋。定義以下向量，從左到右比較，第一個不同分量較小者較佳：

```
S = [
 R(非自願單節), Q(非自願單節),
 R(AC), Q(AC),
 max(R(BC), R(AB)), R(BC)+R(AB), Q(BC)+Q(AB),
 R(工時), Q(工時)
]
```

D1 優先序已依使用者明確修訂：非自願單節班最優先，其次 AC，再其次 BC/AB 同級，最後工時。R/Q 是將順序落實為可測比較器的工程定義，不將低優先指標改善抵銷高優先指標惡化；BC/AB 同級內先看最嚴重差距，再看合計差距與離散程度。

有人在某週請假多天時，不要求該週 AC/BC 與其他人相同；所有調整仍尊重休假及固定班。整月指標用於合法候選的比較，不能為湊相同次數違反意願。固定限制若令差距無法消除，保留原因，不把它虛報為演算法已達完全公平。

公平性階段保持每個日期/班別/站別的修補後人數，僅轉移/交換未鎖定骨科人員。只接受 S 嚴格下降的整組候選；同 S 不接受，只在同等改善的候選間選修改最少者，再按固定順序決定。不得藉刪班、任意加班或移動小兒班來縮小差距。固定意願造成的差距仍統計，報告加註不可動來源，不擅自扣除小兒負擔。

## 6. 搜尋界限與可重現性

第一版預設提案：每階段最多評估 20,000 個完整候選、最多接受 200 次調整，整個後處理共享 10 秒安全時間預算；以設定物件集中定義，測試可注入計時器及縮小預算。這些是待本機/Apps Script 量測後調整的工程初值 D2，非效能保證。

決策主要按固定候選次序及評估次數限制，可重現測試固定預算並使用假時間；實際時間限制只作安全中止，輸出必須標明可能造成不同停止點。

覆蓋搜尋到限且未達標：不儲存，回報 SEARCH_LIMIT。公平性搜尋到限：若已有完整合法且覆蓋合格的最佳班表，可儲存該班表，但報告註明公平性未搜完。無改善候選不表示全域最優。明確輸入衝突、搜尋未找到方案、搜尋超時、內部資料不一致須分別回報。

## 7. 結果契約與調整歷程

成功仍回傳原有 context，附加 adjustmentReport，不改既有 Library 函式名稱。報告至少包含：input/baseline 版本識別、各階段 S 與逐人原始指標、覆蓋缺失、調整前後位置/來源/原因、候選評估數、接受次數、耗時及停止原因。

錯誤具有可序列化 code/details，保留既有錯誤拋出方式；代碼包括 INPUT_CONFLICT、COVERAGE_UNRESOLVED、SEARCH_LIMIT、INTERNAL_INVALID、PERSISTENCE_FAILED。輸出詳細日期/班別/員工限制，有限搜尋未找到不得稱不可行證明。

三段比較：initial → coverageRepaired → fairnessAdjusted；最終 S 不得比 coverageRepaired 差。報告分別列規則通過與搜尋完成，不以「函式回傳」當成所有規則成功。

## 8. 儲存與重試的流程整合

目前 flow_run.js 在排班前更新 FT_WINDOW_CLOSED，若排班失敗再次呼叫 closeFtWindow 會被原狀態判斷拒絕。需納入獨立任務，不能只改引擎 throw。

D3 行為依使用者修訂：失敗必須還原到「選填已關閉、排班尚未觸發/可重新觸發」狀態，不是只維持某個無法再觸發的失敗或執行中狀態。

本機目前沒有獨立排班中狀態，只有 RUN_CREATED、FT_WINDOW_OPEN、FT_WINDOW_CLOSED、PUBLISHED 等既有值；先使用 FT_WINDOW_CLOSED 定義重試就緒點，不在此規格擅自新增狀態列舉。保留 closeFtWindow 名稱與成功字串，入口須同時接受 OPEN（首次截止）與 CLOSED（排班重試），PUBLISHED 與其他狀態仍禁止。

1. 首次執行：OPEN → 完成關閉選填 → CLOSED；保存首次截止時間，此時才捕捉 stateBeforeScheduling=CLOSED。不是捕捉原始 OPEN 作為失敗還原值。
2. 排班執行：使用同一次意願快照。若實作階段切換執行中的狀態，失敗時必須明確還原 stateBeforeScheduling；目前未切中間狀態也要驗證最終仍為 CLOSED。
3. 排班/覆蓋/驗證失敗：還原或確認 CLOSED，保留首次截止時間，記錄失敗階段，讓原入口能再觸發；不刪舊班表、不匯出、不顯示成功。
4. 寫入/匯出失敗：仍須還原 CLOSED 並明確揭露可能部分寫入的階段，不將狀態還原誤稱為 Sheet 資料已回復。若狀態還原本身失敗，回報原始及還原兩個錯誤，不能宣稱可立即重試。
5. 重試：CLOSED → 對當下資料建立新快照 → 排班；不得重開選填、覆寫首次截止或重複發布。成功後保留目前既有 CLOSED 到另行發布 PUBLISHED 的流程，不新增成功狀態。
6. 截止動作本身若失敗且仍是 OPEN，不得進入排班或宣稱選填已關閉，這與排班開始後的失敗分開處理。

此外，目前 processFtSubmission 直接寫入而沒有驗證開放狀態；僅不顯示新選填頁面不足以保證關閉。需新增後端狀態檢查，拒絕已開啟舊網頁在 CLOSED 或其他非 OPEN 狀態提交，維持「仍關閉選填」的要求。狀態檢查與實際寫入/截止需使用同一套互斥機制，避免檢查後恰逢截止的競爭；不需要新增 Sheet 欄位。

來源驗證和輸出列準備必須在任何舊資料清除前完成。狀態及還原只作用於同一 runId 的當次操作，不得覆寫另一個已成功發布的任務狀態。

Google Sheets 多次寫入沒有在本案承諾原子交易：實際 I/O 失敗可能造成部分寫入。需記錄 runId、失敗階段、舊目標資料快照，明確回報而非宣稱舊資料必然未動；驗收保證的是寫入前驗證失敗零寫入，與假服務的 I/O 錯誤不回報成功。跨程序交易/持久化恢復不在本次範圍。

| I3 | 假 Sheet 寫入或匯出失敗 | 不回報成功，保留失敗階段及恢復所需快照 |

100 組的目標為全部硬條件達標；若存在尚未解決或預算中止，必須逐案列出並回報，不能以單元測試通過宣稱整體完成。對可直接補及小型交換的已知案例必須達標；必要時用獨立的當日窮舉測試確認已知小案例確實有可行解，不能拿與搜尋相同的程式當唯一正確性依據。

## 10. 技術、指令與邊界

沿用 Google Apps Script JavaScript、SchedulingEngine 物件及 Node node:test/assert/vm。正式碼位於根目錄，測試與假服務在 tests/、tests/support/；規格及任務在 tasks/。例：共同驗證可採 `validateSchedule(context, { requireMinimumCoverage: false })`，各階段顯式指定模式；實作命名需與現有物件方法風格一致。

實作後的完整命令：

```sh
node --test tests/*.test.cjs
TZ=Asia/Taipei node tests/evaluate-adjustments.cjs
git diff --check
```

`evaluate-adjustments.cjs` 是待新增測試入口，不是目前已存在的工具。它讀凍結基準並輸出新的報告檔，不覆寫歷史報告。沒有本機 Apps Script 建置指令；Node 假服務不等同線上驗證。

必須：分階段驗證、逐人鎖定、一致統計、候選原子試算、保留失敗與基準、達標後才儲存。已依使用者修訂：D1 單節→AC→BC/AB→工時；D3 失敗還原可重試且關閉選填的狀態。D2 搜尋初值仍待確認；D3 不新增狀態名稱，另列目前 CLOSED 的落實方式與失敗驗收。不得：改意願以湊班、消除不喜歡的失敗案例、搬動 PEDS、改 Sheet 欄位/輪轉、偷偷發布線上版本。
