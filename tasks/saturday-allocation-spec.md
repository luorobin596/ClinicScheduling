# 規格：週六依整日方案與工時達成率分配

狀態：2026-10-19 使用者已授權實作；週六分配及報表已完成本機程式與測試，400 組比較結果見 tests/results/summary.md。未部署線上 Library。
現行結構政策以 §16（2026-10-20 最大可行 AB）為準；前文五人100是原合法方案數，現在只有30個最大配對方案需公平性評分。
基準檢查點：`ced9647f452dcf3c284a6ad3abeb2fcc67969b34`。

本次只規劃週六首次分配。正式公平性定義沿用 [覆蓋與公平性規格](coverage-fairness-spec.md)；來源與鎖定沿用 [指派來源規格](staff-assignment-provenance-spec.md)。本規格是週六分配的增補，沒有取代已完成的 20 項來源／修補任務。

## 1. 目標、依據與範圍

使用者已同意：週六需要考慮工時達成率；整組雙班移轉留待擴大測試後再決定。採用前述整日方案比較及合法組合生成方向，先以規格供審閱。

目前週六依非自願單節積分排序，再逐人先 A 後 B 填入；拿到 AB 或輪空均不增加積分，可能多個週六重複取得相同優先位置。同分沿用 Staff 列順序。診斷顯示只休全天情境 FT001／FT004 平日結束平均 124.00／138.28 小時，週六後反轉為 150.96／143.96 小時。詳見 [偏差診斷](../tests/results/hours-bias-analysis.md)。

目標：在相同合法週六名額下，以排班後的公平性結果選人，使工時達成率參與週六決策，避免直接把既有單節積分當成取得 AB 的優先資格。

本次範圍：週六目標人數、合法 A／B 人員組合、整日方案評分、增量統計、完全同分輪轉、診斷與同批比較。平日 C → AC → A → B、既有最低覆蓋修補及公平性後處理均保留。使用者已確認報表定義並授權開始編寫；下列工程初值隨規格實作，仍須以量測披露限制。

## 2. 執行環境與介面

- Google Apps Script V8；既有全域物件與四小時班次；不新增第三方依賴。
- 預計新增 `scheduling_saturday.js`，全域物件 `SaturdayAllocator`；`SchedulingEngine._assignSaturdayShifts(context, singleShiftCounts)` 保留既有簽章，轉接新模組。舊統計參數不再決定排序；以共用統計為準。
- 建議模組介面：`allocate(context, staff, options) -> { context, report }`。在副本完成整個週六階段；成功才由引擎接收，不在候選迴圈修改原始 context。
- 不增加 Sheet 欄位、不改前台 API、不讀寫線上資料、不寄信、不變更狀態機、不部署 Library。
- Staff 人數動態處理，不硬編碼五人或 FT001／FT004。

## 3. 輸入與硬條件

輸入為平日 B 已完成的 context，含原始 constraints、每人來源、Staff 快照、月曆及已填入的全部固定班。所有原始意願與固定小兒班保持不可變。

必須遵守：

1. 指定上班、休假、固定班及小兒班不動；候選只新增當日未鎖定骨科班。
2. 每人每天最多兩班，同時段不可跨科重複。
3. 骨科週六 A／B 上限讀既有 `RulesConfig.SHIFTS.SATURDAY`；目前 A3／B2，小兒不計入骨科人數。
4. 每個營業週六至少一位骨科員工；固定指派計入人數，不重複新增。
5. 比較公平性前先固定當日 A／B 目標人數；不得藉少排班降低工時差距。
6. 工時基準 C 由原始休假計算並固定；骨科及小兒均計 H；C=0／未知資料沿用共用統計的 N/A、警示及錯誤規則。

呼叫 `ScheduleAdjustments.validate(..., { requireMinimumCoverage: false })` 檢查硬限制；不能在週六階段要求所有平日已達最低覆蓋，因平日缺失仍由後續 repair 處理。

## 4. 日期順序及固定目標人數

### 4.1 日期順序

沿用較難排的週六先處理：從階段輸入計算每個週六可新增 A 或 B 的不同員工數，由少到多；同供給量按日期。所有固定班保留。紀錄實際處理順序，不能把它誤稱為日曆先後順序。

每完成一天即更新統計；其餘未處理週六只包含原本固定班，不假設未來一定取得 AB，也不預測未來自動工時。這是逐日選擇，不宣稱全月週六聯合最優。

### 4.2 目標人數

對 A／B 分別計算：

- `locked_s`：已存在的當日骨科指定人員集合。
- `eligible_s`：能在保留既有全部固定班的前提下，合法值該骨科班的 FT 集合；已指定該班者只計一次。計算 eligible 必須包含 locked；不能直接用會排除「已在該班」的可新增判斷而漏算固定人員。
- `target_s = min(req_s, |eligible_s|)`，須滿足 `|locked_s| <= target_s`。

在目前週六只有 A／B、每人最多兩班的規則下，A／B 目標可同時達成；讓可合法配置的名額先固定，再比較人員，不以公平性評分自行減少目標。若供給不足，只填可行名額並保留缺額給兼職，不強迫達到 A3／B2。

若未來其他固定站別或新限制造成兩個目標不能同時實現，需回報 `SATURDAY_TARGET_UNREACHABLE` 與診斷，不默默降低其中一班或自創 A／B 優先規則；另行修訂目標政策。無任何骨科人員可排則回報明確輸入衝突，遵循既有失敗重試流程。

## 5. 直接產生合法整日方案

先固定每班的指定人員，只從該班可新增的人選中選足剩餘名額。每個候選以 `A: staffId[]`、`B: staffId[]` 表示；人員在同一班只可出現一次。A／B 集合可以重疊，重疊即 AB。

五人全可上、無指定時：A 選三人有 10 種，B 選兩人有 10 種，共 100 個方案；不先產生 1,024 個人別狀態再全部篩選。四個週六為約 400 個方案。這是特定輸入的數量，不是動態 N 的固定上限。

若某班剩餘名額為 0，應有唯一的空新增組合，不可誤認為無候選。候選生成順序以 staff_id 正規化排序，與 Sheet 列順序無關。先檢查便宜的局部硬限制，再計分；每個選中方案提交前仍需跑完整共用驗證。

## 6. 評分：保留原公平性優先序

對每個方案計算「已完成平日＋已決定週六＋本日候選＋其他日原本固定班」的結果，完整沿用 `ScheduleFairness` 的向量及數值比較：

```
月非自願單節 R、Q
→ 月工時達成率 R、Q
→ 每週 AC 的既有彙整
→ 每週 BC／AB 同級的既有彙整
```

R 為最大值減最小值；Q 為既有離散程度。每個分量按字典序比較，數值容忍沿用 1e-9。所有 R／Q 均比較全體合格 FT，不只比較當天可排的人。

- 自願半天單節排除；小兒造成的非自願單節納入；指定雙班納入每週班型。
- 同樣的單節 R／Q 下，選工時達成率 R／Q 較小的方案；不得跳過 Q 直接比較工時。
- 單節公平性更好時，仍可接受工時較差；這是既有優先序，不承諾每個方案的工時都改善。
- 工時達成率相同且高優先項也相同，才比較每週班型；週日至週六切週，含短週。
- 週六首次分配是在合法候選間選最小向量，不套用後處理「必須比未排班時嚴格改善」的規則，否則可能因新增工作被錯誤拒絕。

評分包含全部既有來源，不從分母扣除尚未排到的空班；不加入新的加權總分、特殊員工補償分數或跨次模擬平均作為排班輸入。

## 7. 增量評分與效能

### 7.1 快取與等價性

階段開始時用正式共用統計建基準，保存每人 H／C／單節及各週班型。候選只重算本日各員工的原指派與候選指派差異，再更新月 H、單節及該週班型。所有未來固定班已包含於基準，不能在處理該日時重複加算。

候選可對 N 位員工重算 R／Q，不對每個方案重新掃描整個月份。增量評分必須與完整 `ScheduleFairness.measure` 逐項一致；不能為了效能另造口徑。優先以共用日別貢獻或彙整 helper 減少重複規則，完整統計作測試 oracle。

只有最終選中方案需要建立完整指派副本與逐人 metadata，再作完整驗證；不要對 100 個候選各深複製全月 context。

### 7.2 搜尋界限與停止

本提案工程初值：每個週六最多評估 20,000 個合法完整方案，整個週六階段共享 2,000ms 安全期限；集中在可注入的設定物件，時間來源可注入。這些數值待審閱與量測，不是 Apps Script 效能保證。它們獨立於既有 repair／improve 的 20,000／200／10 秒設定，不偷偷扣用或擴大後處理預算。

到限但已找到完整合法日方案：採用已評估中的最佳方案，標示 `CANDIDATE_LIMIT`／`TIME_LIMIT`，不能稱為完整枚舉最優。整個階段期限不足以處理剩餘日期、或尚無合法完整方案：回報帶有階段與日期的 `SEARCH_LIMIT`；不回退舊貪婪算法、不提交半套週六結果、不寫 Sheet。無候選與搜尋到限需區分，不能因到限宣稱輸入無解。

正常五人案例應完整評估所有合法方案；若 400 組常態遇到限額，不符合本次效率目標，須先分析而非直接提高上限。量測平均／P95／最大耗時、合法候選數及完整掃月次數；同機暖機後比較舊週六、新週六與完整管線。Node 假服務與 GAS 實際耗時分開報告。

## 8. 完全同分的輪轉

只有整個公平性向量相同時，才使用輪轉決勝。以該週六在當月日曆的 weekIndex，呼叫既有 `_getWeeklyStaffOrder` 取得 ID 排序後的正反序；不得按「第幾個被處理的週六」算輪轉，避免難排日期順序改變名次。

建議確定性規則：依輪轉人員順序比較候選的本日實際總班數，第一位不同者較多班的方案優先；全部相同時，按該順序的 A／B 指派位元固定比較（A 優先），最後按正規化 staff_id 列表。這只決定評分完全相同的方案，不抵銷任何公平性差異，也不碰鎖定班。

上述完全同分規則與 §7 搜尋初值為本規格工程選擇，已隨使用者整體實作授權採用；不是另有業務公平性權重。

## 9. 指派來源、提交與報告

選中方案的新增 A／B 仍用 `ScheduleAssignments.add`，來源保留 `AUTO_SAT_A`／`AUTO_SAT_B`；原固定來源、originalSource、鎖定均不覆寫。不增加新的 Sheet 欄位。

整個週六配置先在隔離 context 上完成，再驗證並交回初始引擎；後續 repair／improve 沿用原流程及原候選，**不新增整組雙班移轉**。

建議 `context.saturdayAllocationReport` 包含：

- 日期處理順序、該日目標／實際 A／B 人數、指定與新增人員。
- 每日合法評估數、是否完整枚舉、停止原因及耗時。
- 所選方案的公平性向量、用到同分決勝與否及當週輪轉順序。
- 階段前後每人 H／C／達成率、單節、AB／A／B／輪空次數；零分母與未知資料警示。

報告保存在回傳 context／離線檔，不在本階段另寫一張 Sheet。全月後處理仍可能改動自動週六班，因此必須同時報告週六完成與最終結果，不能把兩者混為一談。

## 12. 比較報告與完成條件

以 `ced9647` 的四份 inputs.json 為固定 cohort，先核對輸入 hash。既有基準有 1 組真實輸入衝突：必須保留並分開報告；公平性比較只用新舊共同成功的同一組樣本，明列分母，不使用兩邊不同樣本平均互相比較。

每階段列每人月 H／C／達成率、非自願單節、每週 AC／BC／AB、週六 AB／單節／輪空，以及每組班表內 R／Q 的分布。另列 FT001−FT004 與全員對全體平均的偏差，不能只看兩人的跨次平均接近就宣稱公平。連休者 C=152、其餘 C=168；自願單節排除。

完成條件：硬限制無新增違規、可行案例最低覆蓋不退步；增量與完整評分一致；五人常態完整枚舉；報告候選／時間上限及效率。期望縮小工時達成率偏差，但不預先保證四情境或每一組都改善。若單節優先令工時退步、日期貪婪選擇造成月結果仍不理想，必須逐項揭露，停在評估結果，不自行加入雙班移轉或更改優先序。

## 13. 程式風格與邊界

沿用兩空白縮排、`var` 全域模組、方法內 `const`／`let`、camelCase；用既有 error helper 保留 code／details。例：

```js
var SaturdayAllocator = {
  allocate: function(context, staff, options) {
    // 先建固定人數與統計快照，再比較候選，最後驗證回傳副本。
  }
};
```

必做：測試先行、共用評分、鎖定不可變、固定樣本、可重現與停止診斷。
需另行確認：公平性優先序變更、週六目標人數政策變更、擴充跨日搜尋或雙班移轉、線上部署。
禁止：改原始意願湊公平、減少名額美化指標、重抽樣消除失敗、改歷史證據、宣稱局部／全域最優而未完整搜尋。

最大配對由原始限制及給定 A／B 人數求得，不將目前自動名單當固定人員。使用每人 0/A/B/AB 合法狀態、以 A／B 計數為狀態的動態規劃求精確上界；常態上限 A3／B2 僅 12 個計數狀態。原始候選仍可直接由組合產生，先排除未達最大配對者，再做公平性計分。五人全可上時 100 個合法原始方案中，僅 30 個需要評分；即使評分到限，已選方案也必須達到已證明的最大配對數。
